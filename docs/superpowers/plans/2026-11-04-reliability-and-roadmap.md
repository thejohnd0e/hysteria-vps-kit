# hysteria-vps-kit: план надёжности и дальнейшего развития

> **Для исполнителя:** выполнять задачи последовательно с помощью навыка `executing-plans` либо, при выбранном пользователем делегировании, `subagent-driven-development`. Этот файл фиксирует объём работ; его создание не является разрешением на реализацию или изменения действующих VPS.

**Цель:** сначала устранить риски существующих операций, затем добавлять полезные возможности, сохраняя небольшой Bash-набор.

**Архитектура:** существующие entrypoint-скрипты и общие функции; единая блокировка изменяющих операций, подготовка файлов отдельно от рабочих и согласованное восстановление при сбоях. Не переносить большой framework транзакций и снимков из xray-vps-kit и не переписывать проект целиком.

**Технологии:** Bash, jq, OpenSSL, systemd, flock, UFW при наличии; ShellCheck и Linux sandbox-тесты.

**Основание:** согласованный в разговоре двухэтапный план от 2026-11-04; замечания из `rew.txt`, сверенные с текущими исходниками. Оценка была статической: аварийные сценарии в рамках обсуждения не воспроизводились. `rew.txt` — исходный материал, а не обязательный к реализации roadmap.

## Общие ограничения

- Основная ветка — `master`.
- Перед реализацией прочитать `AGENTS.md`, `STATUS.md`, `DECISIONS.md`, `TODO.md` и проверить изменения рабочего дерева.
- Сохранять существующих клиентов, сертификат, ключ, pin, endpoint и пароль обфускации, кроме явно запрошенных изменений.
- Не печатать и не коммитить пароли, сертификаты и реальные клиентские профили. В тестах использовать синтетические данные.
- Не менять действующие VPS, не перезапускать их службы и не проводить на них аварийные тесты без отдельного согласования.
- Изменения клиентов по-прежнему требуют перезапуска службы; не обещать бесшовного применения.
- Sandbox-тесты выполнять на Linux; Windows Git Bash не является подходящей средой для этих наборов.
- Прежнее решение об отсутствии транзакций и учёта владения ресурсами в `DECISIONS.md` пересмотреть явно, а не обходить молча.
- Каждое исправление сопровождать тестом: сначала воспроизведение дефекта, затем минимальное исправление и проверка отсутствия регрессий.

## Особое внимание при проверке

- Удаление клиента не должно молча восстанавливать отозванный доступ при откате.
- Блокировка должна сохранять корректность при повторном запуске updater через `exec`.
- Ошибка восстановления должна отличаться от исходной ошибки применения и не маскироваться сообщением об успехе.
- Незавершённая установка не должна приводить к перегенерации существующих секретов.
- Удаление установки не должно затрагивать пользователя и firewall-правила, существовавшие до неё.

## Затрагиваемые файлы

| Файл | Ответственность в первом этапе |
|---|---|
| `lib/common.sh` | Валидация, блокировка, проверка состояния, общие функции подготовки и восстановления, генерация unit |
| `install.sh` | Безопасная первоначальная установка и восстановление после сбоя, учёт созданных ресурсов |
| `update.sh` | Согласованное обновление ядра/state/config/unit и восстановление при неудаче |
| `hy2-client` | Проверка имён и безопасное применение добавления/удаления клиентов |
| `uninstall.sh` | Удаление только принадлежащих проекту ресурсов |
| `tests/run.sh` и необходимые дополнительные тестовые скрипты | Проверки дефектов, конкуренции и отказов |
| `README.md`, `STATUS.md`, `DECISIONS.md`, `TODO.md` | Фактическое поведение, ограничения и результаты проверок |

Не дробить `common.sh` на несколько модулей заранее. Если реализация потребует такого разделения, обосновать его отдельно.

## Этап 1. Необходимые исправления

### 1. Валидация и корректность состояния

- [x] Запретить новые имена клиентов, совпадающие без учёта регистра.
- [x] Проверять существующее состояние на такие конфликты; не переименовывать клиентов автоматически.
- [x] Исправить проверку порта: каноническая десятичная запись, диапазон 1–65535.
- [x] Валидировать SNI и endpoint — IPv4 или DNS-имя.
- [x] Не выдавать локальный адрес за подтверждённый публичный endpoint.
- [x] Проверять структуру `state.json` перед изменениями; при повреждении завершаться без перезаписи.
- [x] Добавить проверки конфликтов `Alice` / `alice`, ведущих нулей и границ порта, неправильных DNS-имён, endpoint и повреждённого состояния.

**Критерий готовности:** ошибочные параметры и некорректное состояние не доходят до изменения установки.

### 2. Единая блокировка изменений

- [x] Ввести одну блокировку для установки, обновления, удаления и изменения клиентов.
- [x] Удерживать блокировку на протяжении всей операции, а не только записи JSON.
- [x] Учесть повторный запуск обновляющего скрипта через `exec` без потери защиты и самоблокировки.
- [x] При занятой блокировке выдавать понятное сообщение.
- [x] Проверить параллельные добавления клиентов, конкуренцию разных изменяющих команд и путь updater с `exec`.

**Критерий готовности:** параллельные команды не теряют клиентов и не смешивают изменения.

### 3. Безопасное обновление

- [x] Перед применением сохранять согласованный комплект: ядро, состояние, конфигурацию и unit.
- [x] Готовить новые файлы отдельно от рабочих; проверять доступными для закреплённой версии ядра средствами, не предполагая существования неподдерживаемой команды проверки конфигурации.
- [x] Централизовать генерацию unit и применять её при установке и обновлении.
- [x] После применения выполнять `daemon-reload` при необходимости и проверять запуск службы.
- [x] При ошибке восстанавливать предыдущий согласованный комплект и проверять запуск восстановленной версии.
- [x] Не считать обновление успешным до проверки; не оставлять ложное состояние «актуально» после сбоя.
- [x] Различать ошибку обновления и ошибку восстановления.
- [x] Показывать сообщение о сохранённом предыдущем ядре только при наличии соответствующей копии.
- [x] Проверить отказ запуска новой версии, отказ восстановления, обновление без смены ядра и синхронизацию unit.

**Критерий готовности:** неудачное обновление не оставляет новую версию в состоянии при неработающем сервере; если восстановление тоже не удалось, это явно сообщается.

### 4. Безопасные изменения клиентов

- [x] Применять `state.json` и конфигурацию как согласованный комплект.
- [x] При неудачном добавлении восстанавливать предыдущее состояние и конфигурацию.
- [x] Для удаления определить отдельное поведение: не возвращать отозванный доступ молча. Если применить отзыв невозможно, явно сообщать об этом; безопасный вариант может потребовать остановки службы.
- [x] До реализации согласовать конкретное поведение удаления при отказе применения и его последствия для остальных клиентов.
- [x] Сохранять сертификат, pin и пароль обфускации.
- [x] Проверить неудачный restart при добавлении и удалении, отсутствие скрытого восстановления доступа и сохранение остальных идентичностей и секретов.

**Критерий готовности:** нет скрытого расхождения между списком клиентов и работающей конфигурацией; неуспешный отзыв доступа не выглядит успешным.

### 5. Восстановление установки и безопасное удаление

- [x] Различать готовую и незавершённую установку.
- [x] Предусмотреть явное восстановление после сбоя без генерации новых секретов поверх существующих.
- [x] Учитывать, созданы ли системный пользователь и firewall-правило самим проектом.
- [x] Для старых установок без данных о владении выбрать консервативное поведение: не считать неизвестный ресурс автоматически принадлежащим проекту.
- [x] При очистке удалять только принадлежащие проекту ресурсы.
- [x] Создавать файлы с секретами сразу с ограниченными правами, а не только исправлять права после записи.
- [x] Документировать, что удаление sysctl-файла не возвращает текущие значения ядра; не подменять их безусловно системными значениями по умолчанию.
- [x] Проверить сбои до и после создания состояния, повторное восстановление, сохранение сертификата и паролей, заранее существовавших пользователя и UFW-правила.

**Критерий готовности:** сбой установки не требует опасной ручной очистки и не приводит к удалению чужих ресурсов.

### 6. Проверки выпуска и документация

- [x] Выполнить `bash tests/lint.sh`: синтаксис и ShellCheck без ошибок.
- [x] Выполнить `bash tests/run.sh` на Linux: все sandbox-проверки проходят, включая добавленные сценарии отказов.
- [x] На изолированной Debian VM проверить настоящую службу, установку, обновление, восстановление и изменение клиентов.
- [x] Проверить передачу данных через клиент, а не только handshake или состояние `active`.
- [x] Отдельно проверить права файлов и сохранение клиентов, сертификата, pin и обфускации.
- [x] Обновить `STATUS.md`, `DECISIONS.md`, `TODO.md` и README: новое поведение, ограничения, фактически выполненные проверки и непроверенные среды.

**Этап завершён, когда:** исправления подтверждены тестами, поведение при сбоях документировано, рабочие профили сохранены. Развёртывание на действующих VPS — отдельное согласованное действие.

## Этап 2. Дополнения для более поздней реализации

Этот этап — список кандидатов, а не обязательство реализовать всё. Каждая функция требует отдельного уточнения интерфейса и критериев готовности после завершения первого этапа.

| Статус | Приоритет | Дополнение | Назначение и ограничения |
|---|---|---|---|
| [ ] | Высокий | `hy2-client doctor` | Диагностика службы, файлов, прав, сертификата, порта и sysctl без вывода секретов и без автоматических изменений |
| [ ] | Высокий | `backup / restore` | Защищённое резервирование и проверяемое восстановление; права root-only, проверка совместимости; не подмена отката обновления |
| [ ] | Средний | `rotate NAME` | Смена пароля клиента без удаления имени |
| [ ] | Средний | `port NUM` | Согласованная смена порта в состоянии, конфигурации и firewall с проверкой конфликтов |
| [ ] | Средний | `logs` | Удобная оболочка над `journalctl` |
| [ ] | Средний | Расширение CI | Автоматические интеграционные проверки Debian/Ubuntu и проверка arm64 |
| [ ] | По потребности | IPv6 endpoints | Корректные URI, YAML и проверки доступности |
| [ ] | По потребности | Статистика | Traffic Stats API на loopback с отдельной защитой |
| [ ] | Экспериментальный | Port hopping | После проверки версии ядра, прав службы, firewall, совместимости клиентов и реальной пользы |
| [ ] | Экспериментальный | ECH | После проверки версии ядра, совместимости клиентов и реальной пользы; не обещать обход блокировок |
| [ ] | По необходимости | Разделение `common.sh` | Выделять модули по мере усложнения, а не создавать структуру заранее |

### Не включать автоматически

- Веб-панель.
- Отдельный сервис HTTP-аутентификации ради hot reload.
- Большой framework снимков и транзакций.
- Изменения сетевых настроек без подтверждённой необходимости.
- Дополнительные ограничения systemd или изменение сертификатов исключительно «для усиления», без проверки совместимости и последствий для действующих профилей.

## Рекомендуемый порядок

1. Полностью завершить этап 1.
2. Добавить `doctor` и `backup/restore`.
3. Выбирать остальные функции второго этапа по практической потребности.

План не предусматривает автоматических коммитов, публикации релиза или развёртывания на серверах без отдельного запроса пользователя.
