# Stage 1 — исправления по результатам проверки (второй проход)

**Вход:** коммит `9f6b8a4` («Reliability Stage 1: locks, safe rollback, repair, validation»), ветка `master`.
**Цель:** устранить дефекты, найденные при независимой проверке этого коммита, не переделывая архитектуру.
**Статус первого прохода:** не готов к выпуску и не подлежит раскатке на серверы.

Прочитай `AGENTS.md`, `docs/superpowers/plans/2026-11-04-reliability-and-roadmap.md` (этап 1) и текущий код перед изменениями.

Проверяющий прогнал набор на Debian 13 VM (`103 passed, 0 failed`) и подтвердил, что перечисленные механизмы работают. Не переписывай их:

## Блокеры

### Блокер 1. Неудачное обновление оставляет ложное «актуально» и не оставляет резервной копии

**Где:** `update.sh:100–112`, `update.sh:52–55`.

**Сейчас:** новый `version`/`core` пишутся в `state.json` (строка 102) до `hvk_render_config` (104) и `hvk_restart_service` (106). При любом сбое между ними `set -e` завершает скрипт через `trap cleanup_backup EXIT`, который **удаляет** резервную копию. В итоге состояние объявляет неработавшую версию, а следующий запуск видит совпадение и говорит «up to date».

**Воспроизведение (Linux, sandbox):**

```bash
U=$(mktemp -d)
bash install.sh --no-service --root "$U" --non-interactive --endpoint 203.0.113.7 >/dev/null
E="$U/etc/hysteria-vps-kit"
jq '.version="0.0.9"' "$E/state.json" > "$U/y" && mv "$U/y" "$E/state.json"
mkdir "$E/config.yaml.new"            # заставляет hvk_render_config упасть после записи state
env HVK_ROOT="$U" bash update.sh; echo "exit=$?"
jq -r .version "$E/state.json"        # 0.1.1 — версия, которая не запускалась
find "$E" -name '.backup-update.*'    # пусто
rmdir "$E/config.yaml.new"
env HVK_ROOT="$U" bash update.sh      # "up to date"
```

Наблюдаемый результат проверяющего: `update_exit=1`, `state_version=0.1.1`, `backup_dirs_left=0`, затем `up to date`.

**Требуется:**

1. Ввести признак незавершённого применения: перед изменением файлов писать `status: "updating"`, а `status: "ready"` — только после успешной проверки службы.
2. Любой вход (`update.sh`, `update.sh --check`) должен считать `status != "ready"` поводом применить/повторить работу, а не сообщать «up to date».
3. Резервную копию сохранять при любом неуспешном завершении и печатать её путь; удалять только после подтверждённого успеха.
4. Любой сбой применения после первой записи (рендер, unit, `daemon-reload`), а не только сбой рестарта, должен вести к откату. Используй явные проверки/`trap ERR`, а не полагайся на `set -e`.
5. Откат не должен удалять `hysteria.previous`.

**Приёмка:** повторение сценария выше даёт: ненулевой код возврата, `status != "ready"`, сохранённую резервную копию, а следующий `update.sh` **применяет** изменения, а не сообщает «up to date». Добавить этот сценарий в `tests/run.sh` как отдельную проверку.

### Блокер 2. `--repair` перегенерирует сертификат и pin, оставляя клиентов

**Где:** `install.sh:188–201`, сообщение об успехе `install.sh:280`; README (`--repair`) и `STATUS.md:9` обещают «без перегенерации секретов».

**Сейчас:** `need_cert` проверяет только наличие обоих файлов и что сертификат парсится. Совпадение ключа с сертификатом не проверяется; новый pin со старым не сравнивается. Если `server.key` потерян, repair создаёт новую пару, записывает новый pin (`install.sh:242`) и рапортует обычный успех. Все выданные URI/QR/YAML при этом перестают работать.

**Воспроизведение:**

```bash
S=$(mktemp -d)
bash install.sh --no-service --root "$S" --non-interactive --endpoint 203.0.113.7 --first-client user1 >/dev/null
P1=$(jq -r .pin "$S/etc/hysteria-vps-kit/state.json")
rm -f "$S/etc/hysteria-vps-kit/server.key"
jq '.status="installing"' "$S/etc/hysteria-vps-kit/state.json" > "$S/x" && mv "$S/x" "$S/etc/hysteria-vps-kit/state.json"
bash install.sh --no-service --root "$S" --non-interactive --repair; echo "exit=$?"
jq -r .pin "$S/etc/hysteria-vps-kit/state.json"; jq -c '.clients|keys' "$S/etc/hysteria-vps-kit/state.json"
```

Наблюдаемый результат: `repair_exit=0`, pin изменился, `clients=["user1"]`.

**Требуется:**

1. Проверять, что ключ соответствует сертификату (`openssl x509 -pubkey` против `openssl pkey -pubout`).
2. При отсутствии/несовпадении пары **не перегенерировать молча**: завершаться с понятной ошибкой, объясняющей, что клиентские профили придётся выдать заново.
3. Перегенерация — только по явному флагу (например, `--force-secrets`) с подтверждением в интерактивном режиме.
4. Если pin всё же изменился, печатать старый и новый pin и предупреждение, что все выданные профили недействительны.
5. Привести README и `STATUS.md` в соответствие с фактическим поведением.

**Приёмка:** сценарий выше без флага завершается ошибкой и **не меняет** сертификат, ключ и pin; с флагом — меняет и громко предупреждает. Оба случая добавить в `tests/run.sh`.

## Важные исправления

### 1. Тесты не изолированы и могут менять checkout разработчика

**Где:** `tests/run.sh:189–215`.

`suite_update` запускает настоящий `update.sh` в рабочем дереве. Скрипт видит `.git` (`update.sh:36`) и делает `git fetch`; при отставании — `git pull --ff-only` **в каталог разработчика**. На detached HEAD (PR в CI) набор падает. Заголовок файла «nothing here touches… the network» неверен.

Проверено: на копии без `.git` — 103/103; на checkout с `.git` — `suite: update`, `FAIL update --check reports up to date`, дальше `fatal`.

**Сделать:** запускать тесты на копии дерева без `.git` (`cp -a` с исключением или `git archive`), либо добавить в `update.sh` явный `--no-git` и использовать его в тестах. Ни один тест не должен обращаться к сети и не должен изменять рабочее дерево.

**Приёмка:** `bash tests/run.sh` проходит и в checkout с `.git`, и в копии без него; после прогона `git status` чист.

### 2. Проверка доменов зависит от содержимого текущего каталога

**Где:** `lib/common.sh:83–85` (`IFS=.; set -- $domain`).

Подстановка имён файлов включена: `*` и `*.example.com` принимаются, если в каталоге есть имена без точек. Установка через `curl | bash` выполняет `cd /`, где это так.

Воспроизведение:

```bash
mkdir -p /tmp/gd && cd /tmp/gd && touch bin etc usr
bash -c 'source /path/to/lib/common.sh; hvk_valid_domain "*" && echo ACCEPT'
```

Наблюдаемый результат: `ACCEPT: *`, `ACCEPT: *.example.com`, `ACCEPT: www.bing.com`.

**Сделать:** отключить глоббинг при разборе (`set -f` / `set +f` вокруг сплита или разбор без `set --`), добавить в `suite_validation` отказ для `*` и `*.example.com`.

### 3. `remove` не закрыт fail-closed при сбое рендера

**Где:** `hy2-client:66–78`.

Резервная копия снимается только в `add` (`:49–52`). Если `hvk_render_config` упадёт после `del(.clients[...])`, команда завершится ошибкой, состояние уже без клиента, а работающий сервер всё ещё его авторизует — ровно то расхождение, которое план запрещает.

**Сделать:** снимать резервную копию и в `remove`; при любом сбое после записи применять ту же политику, что при сбое рестарта: не возвращать доступ, остановить службу и явно сообщить.

### 4. `--repair` не валидирует состояние

**Где:** `install.sh:86` (`|| echo ready`) и `install.sh:100`.

Повреждённый JSON: репair падает сырой ошибкой jq; обычный install на том же файле говорит «already installed». Структурно неверное состояние принимается, переписывается и помечается `ready`.

**Сделать:** вызывать `hvk_validate_state` до чтения полей; повреждённое состояние — одна понятная ошибка без перезаписи; не маскировать ошибку разбора как `ready`.

### 5. `config.yaml` сначала создаётся 0644

**Где:** `lib/common.sh:254–255`.

Пароли клиентов и обфускации пишутся в файл до `chmod 640`. Каталог 0750 ограничивает доступ, но пункт плана «сразу с ограниченными правами» не выполнен; при падении остаётся `.new` с широкими правами.

**Сделать:** `umask 077` вокруг блока либо `install -m 640 /dev/null "$HVK_CONFIG.new"` до записи; удалять `.new` при ошибке.

### 6. `VERSION` не поднят

Остался `0.1.1`. `update.sh:46` сравнивает `state.version` с `VERSION`; на действующих хостах после `git pull` будет «up to date», и синхронизация unit/изменения этапа не применятся к состоянию.

**Сделать:** поднять `VERSION` (например, `0.2.0`) и упомянуть это в README/`STATUS.md`.

## Проверки и критерии готовности

Обязательно выполнить и приложить вывод:

1. `bash tests/lint.sh` — ShellCheck чистый.
2. `bash tests/run.sh` — все проверки проходят **в checkout с `.git`**; после прогона `git status` не содержит изменений.
3. Новые регрессионные проверки на: сбой обновления после записи state, repair без ключа (без флага и с флагом), `*`/`*.example.com`, сбой рендера при `remove`, повреждённый state + `--repair`.
4. На изолированной Debian VM — настоящая служба: установка, обновление, восстановление, add/remove, передача данных через клиент (не только handshake).

**Готово, когда:** оба блокера воспроизведены до исправления и не воспроизводятся после; документация не обещает больше, чем делает код; VERSION поднят; действующие серверы не тронуты.

**Вне рамок:** этап 2 плана (`doctor`, `backup/restore`, `rotate`, `port`, `logs`, IPv6, ECH, port hopping), изменение аутентификации, схемы pinning и systemd-ограничений, раскатка на VPS.
